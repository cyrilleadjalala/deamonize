# Requirements Document

## Introduction

Today a person who wants to turn a web application workflow into an MCP tool must use the terminal: `daemonize record`, `daemonize compile`, `DAEMONIZE_SECRET_*` environment variables and a hand-written MCP JSON entry. This feature lets a non-technical user run the whole cycle from the Daemonize Studio UI: start Daemonize, describe an action, record it in a visible browser, have it compiled automatically, enter credentials in a guided panel, test the tool, and connect it to Kiro or another MCP client.

The feature adds to the Studio. Every existing CLI command and flag stays unchanged. The current Studio security model stays in force: loopback listening by default, a per-process token with an HttpOnly, SameSite=Strict cookie, Host check, Origin check, the `x-studio-request` header on every POST, CSP `default-src 'self'`, `redactForStudio` and `knownSecretValues`, and no secret value in any response, log line or artifact.

This spec builds on the `studio-first-recording-fixes` spec. It reuses the recording panel, `RecordOptions.signal`, `completeRecording`, the `LiveRecorder.requestEnd('api')` end path, and the configured/missing secret status exposed by `PlaygroundSession.configuredSecretVariables()`.

Decisions left to the design phase: the mechanism that protects the local secret store (Windows DPAPI, macOS Keychain, libsecret, or AES-GCM with a key held in the OS store) and the exact location of the application data folder per platform. The Power install file layout is fixed by Requirement 11, Criterion 4. The design must confirm that the workspace skills location `.kiro/skills/<name>/SKILL.md` is the location Kiro reads.

## Glossary

- **Daemonize_CLI**: The `daemonize` command-line program built in `src/cli/index.ts`.
- **Studio**: The local web application and its JSON API served by `startStudio` in `src/studio/server.ts`.
- **Studio_API**: The `/api/*` routes of the Studio.
- **Studio_UI**: The single-page interface served from `src/studio/ui/`.
- **Studio_Guard**: The set of request protections of the Studio: per-process token (header or HttpOnly SameSite=Strict cookie), Host check, Origin check, `x-studio-request` header on POST, request size limits, and the CSP.
- **Redactor**: `redactForStudio` and the `knownSecretValues` scrubber that remove secret values from every Studio response.
- **Workflow_File**: The file `daemonize.workflows.json` that holds recorded workflows.
- **Output_Dir**: The directory `daemonize-out/` (or the one given to `studio`) that `compile` writes to.
- **Action**: One recorded workflow, which becomes one MCP tool. The user names it.
- **Tool_Name**: The snake_case name that the compiler derives from the Action name, made unique with the suffixes `_2`, `_3`, and so on.
- **Recording_Session**: One Studio-started recording, from the start request until the state is `done` or `error`.
- **Recording_Manager**: The Studio component that owns the single Recording_Session and drives `record()`.
- **Recording_State**: One of `idle`, `recording`, `saving`, `compiling`, `done`, `error`.
- **Recording_Panel**: The in-page panel shown in the recording browser, defined by the `studio-first-recording-fixes` spec.
- **Browser_Launcher**: The component that chooses and starts the browser for recording.
- **App_Data_Dir**: A per-user local application data folder outside every repository and outside the Output_Dir, one per operating system (for example `%LOCALAPPDATA%\Daemonize`).
- **Session_Store**: The part of the App_Data_Dir that keeps one Playwright storage state per application.
- **Application_Key**: The normalized origin (scheme, host, port) of the URL of an Action. It identifies one application.
- **Secret_Vault**: The write-only local store of secret values, kept in the App_Data_Dir.
- **Secret_Kind**: One of `password`, `totp`, `token`.
- **Secret_Name**: The name of a required secret, such as `TOTP` for `DAEMONIZE_SECRET_TOTP`.
- **Otpauth_URI**: A URI of the form `otpauth://totp/<label>?secret=<Base32>&...`.
- **Base32_Secret**: A string over the RFC 4648 alphabet `A-Z` and `2-7`, optionally padded with `=`.
- **Playground_Session**: `PlaygroundSession` in `src/studio/playground.ts`, which starts the child `mcp-server.js` process.
- **Child_Server**: The `mcp-server.js` process started by the Playground_Session.
- **Compile_Runner**: The Studio component that calls `compile()` for the Output_Dir.
- **Compile_State**: One of `idle`, `running`, `done`, `error`.
- **Kiro_Power**: The Kiro Power generated by `src/compiler/kiro-power-generator.ts`.
- **Power_Installer**: The Studio component that writes the MCP server entry (into `.kiro/settings/mcp.json`) and the skill file of the Kiro_Power into the `.kiro/` folder of a workspace.
- **Target_Workspace**: The workspace folder the user chooses for the Power_Installer.
- **MCP_Config_Snippet**: The JSON text the "Copy MCP configuration" button copies.
- **Secret_Placeholder**: A reference of the form `${DAEMONIZE_SECRET_<NAME>}` that stands for a secret value without containing it.
- **Secret_Scan**: The script `scripts/check-secrets.mjs` (`npm run check:secrets`) and `scripts/lib/secret-scan.mjs`.
- **Plain_Language**: Wording that uses none of the terms {record, compile, storage state, environment variable, MCP, JSON, token, CLI} as a whole word, in a case-insensitive match, on the main path screens, except where the screen explicitly offers a technical option (the "Copy MCP configuration" button).

## Requirements

### Requirement 1: Default launch opens the Studio

**User Story:** As a non-technical user, I want to type `daemonize` and get a window I can use, so that I do not need to know any subcommand.

#### Acceptance Criteria

1. WHEN the user runs `daemonize` with no subcommand, no arguments and no options, THE Daemonize_CLI SHALL start the Studio exactly as `daemonize studio --open` does: Output_Dir `daemonize-out`, Workflow_File `daemonize.workflows.json` in the current directory, host `127.0.0.1`, a free port, and the default graph file `<Output_Dir>/state-graph.json`.
2. WHEN the default launch has started the Studio, THE Daemonize_CLI SHALL print to standard output one line with the Studio address including its per-run token, and one line telling the user that Ctrl+C stops the Studio.
3. WHEN the default launch has started the Studio, THE Daemonize_CLI SHALL ask the operating system to open the Studio address, including its token, in the default browser.
4. IF the operating system cannot open the browser, THEN THE Daemonize_CLI SHALL keep the Studio running, SHALL NOT print an error or change the exit code, and the address line from criterion 2 SHALL remain the user's way to open the Studio.
5. IF the default launch cannot start the Studio (for example, the port cannot be bound), THEN THE Daemonize_CLI SHALL print one line starting with `Error:` that names the cause on standard error and exit with code 1.
6. WHEN the user runs `daemonize` with any existing subcommand (`record`, `compile`, `merge`, `serve`, `studio`, `sandbox`), THE Daemonize_CLI SHALL run that subcommand with the same flags, output and exit codes as before this feature, and SHALL NOT start the default launch.
7. WHEN the user runs `daemonize --help` or `daemonize -h`, THE Daemonize_CLI SHALL print the usage with the list of all existing subcommands, SHALL NOT start the Studio, and SHALL exit with code 0.
8. IF the user runs `daemonize` with an argument or option that is not a known subcommand or option (for example `daemonize foo`), THEN THE Daemonize_CLI SHALL NOT start the Studio, SHALL print an error naming the unknown argument on standard error, and SHALL exit with a non-zero code.
9. WHILE the Studio started by the default launch is running, THE Daemonize_CLI SHALL keep the process alive.
10. WHEN the Daemonize_CLI process receives SIGINT or SIGTERM while the Studio started by the default launch is running, THE Daemonize_CLI SHALL close the Studio (and, through it, any active Recording_Session and Child_Server) and exit with code 0 within 5 seconds.

### Requirement 2: Studio starts without any prior files

**User Story:** As a first-time user, I want the Studio to open in an empty folder, so that I can begin without preparing files.

#### Acceptance Criteria

1. WHEN the Studio starts and the Workflow_File does not exist, THE Studio SHALL start, listen on its port, and serve the Studio_UI without writing to the console or log any error about the missing file.
2. WHEN the Studio starts and the Output_Dir does not exist, THE Studio SHALL start, listen on its port, and serve the Studio_UI without writing to the console or log any error about the missing directory, and THE Studio SHALL NOT create the Output_Dir.
3. WHEN a `GET` or `HEAD` request for `/api/overview`, `/api/workflows`, `/api/graph`, `/api/schemas` or `/api/pbt` arrives and the Workflow_File does not exist, THE Studio_API SHALL answer status 200 with a view that lists zero Actions, whether or not the Output_Dir exists.
4. WHEN a `GET` or `HEAD` request for one of the five routes in Criterion 3 arrives, the Workflow_File exists and holds valid workflow-set JSON, and the Output_Dir does not exist, THE Studio_API SHALL answer status 200 with the Actions of the Workflow_File and with the Output_Dir reported as not compiled.
5. WHERE the Workflow_File is absent, THE Studio_API SHALL answer `/api/pbt` with status 200 and a view that reports zero property-test results and no test run in progress, and SHALL answer `/api/graph` with zero nodes and zero edges.
6. IF the Workflow_File exists but cannot be read as a file, is larger than the size limit that `loadLive` applies, or does not parse as a valid workflow set, THEN THE Studio_API SHALL answer each of the five routes in Criterion 3 with status 500 and a JSON body whose only field is `error`, with a message that names the problem (unreadable, too large, or not a valid workflow set) and contains no part of the file content and no absolute path. THE Studio SHALL keep running and SHALL answer the next request normally once the file is valid.
7. WHEN the Workflow_File, the Output_Dir or its `mcp-server.js` is created, changed or removed after the Studio started, THE Studio_API SHALL reflect the new state in the answer to the next request of each of the five routes in Criterion 3, without a restart and without cached data older than that request.
8. THE Studio_API SHALL answer `GET /api/overview` with three boolean fields: `workflowFileExists` (the Workflow_File exists), `outputCompiled` (`<Output_Dir>/mcp-server.js` exists) and `recordingActive` (the Recording_State is `recording`, `saving` or `compiling`). WHEN no Recording_Manager has been started, `recordingActive` SHALL be false.
9. IF the Workflow_File does not exist and a request arrives for a path under `/api/` that is not one of `/api/health`, `/api/assets/*`, `/api/playground*`, `/api/pbt/run` or the five routes in Criterion 3, THEN THE Studio_API SHALL answer status 404, the same as when the Workflow_File exists. (Exception: the new routes of this spec.)

### Requirement 3: Guided welcome screen and new-action form

**User Story:** As a first-time user, I want a clear first screen that asks me what I want to automate, so that I know what to do next.

#### Acceptance Criteria

1. WHILE `/api/workflows` reports zero Actions, including when the Workflow_File does not exist, THE Studio_UI SHALL show a welcome screen as the content of the Overview route (`#/`), with a primary button labelled "+ New action".
2. WHILE `/api/workflows` reports at least one Action, THE Studio_UI SHALL show a "+ New action" button on the Overview screen.
3. WHEN the user activates "+ New action", THE Studio_UI SHALL show a form with exactly three controls plus the buttons "Start recording" and "Cancel": a text field for the action name, a text field for the web address, and a checkbox labelled "Reuse my signed-in session".
4. WHEN the user activates "Cancel", THE Studio_UI SHALL close the form, send no request, and return focus to the "+ New action" button.
5. THE Studio_UI SHALL associate each control of the form with a programmatically linked visible text label.
6. WHEN the user submits the form, THE Studio_UI SHALL trim leading and trailing whitespace from the action name and the web address before validating them.
7. IF the trimmed action name is empty, is longer than 80 characters (counted as Unicode code points), contains no ASCII letter (`A-Z`, `a-z`) and no ASCII digit (`0-9`), or contains a control character (U+0000 to U+001F or U+007F), THEN THE Studio_UI SHALL show a plain-language message next to the field that names the problem and the next step, keep the entered values, and send no request.
8. IF the trimmed web address is longer than 2048 characters, cannot be parsed as an absolute URL, has a scheme other than `http` or `https`, or contains a user name or a password, THEN THE Studio_UI SHALL show a plain-language message next to the field that names the problem and the next step, keep the entered values, and send no request.
9. IF the action name and the web address are valid, THEN WHEN the user activates "Start recording", THE Studio_UI SHALL send one `POST /api/record/start` whose body holds exactly the action name, the web address and the reuse choice (true when the checkbox is checked, false otherwise).
10. IF the request of `POST /api/record/start` holds an action name or web address that fails Criterion 7 or 8, THEN THE Studio_API SHALL answer status 400 with a plain-language message that names the invalid field, and start no Recording_Session.
11. THE Studio_API SHALL accept an action name that is valid under Criterion 7 even when its derived Tool_Name equals the Tool_Name of an existing Action, or is shortened to 64 characters at a word boundary, because the compiler makes the Tool_Name unique with the suffix `_2`, `_3`, and so on.
12. WHILE no saved session is available for the Application_Key of the entered web address, THE Studio_UI SHALL keep the "Reuse my signed-in session" checkbox enabled and unchecked by default, and SHALL show next to it a hint that no session is saved yet and that this recording will save one when the box is checked.
13. WHEN the web address field changes to a value that parses as a valid `http` or `https` URL, THE Studio_UI SHALL update the saved-session hint of Criterion 12 for the Application_Key of that URL within 1 second, without any request that carries the full web address, only the Application_Key.
14. IF the Studio_API answers `POST /api/record/start` with status 409, 400 or 5xx, THEN THE Studio_UI SHALL keep the form open with the entered values, and show the plain-language message of the response in an element with `role="alert"`.

### Requirement 4: Recording driven from the Studio

**User Story:** As a user, I want to record from the Studio and stop from the Studio or from the browser, so that I never use a terminal.

#### Acceptance Criteria

1. THE Studio_API SHALL expose `POST /api/record/start`, `GET /api/record/status` and `POST /api/record/stop`, and SHALL answer status 405 with an `Allow` header for any other method on these routes.
2. THE Studio_Guard SHALL apply to the three `/api/record/*` routes exactly as it applies to the playground POST routes. A request SHALL be answered with status 401 when it has no valid token. It SHALL be answered with status 401 when it authenticates by cookie only and lacks the `x-studio-request` header or a matching Origin. It SHALL be answered with status 403 for a foreign Host or a foreign Origin. A POST with a non-empty body and a content type other than `application/json` SHALL be answered with status 415. A body larger than 64 KiB SHALL be answered with status 413. A body that is not a JSON object SHALL be answered with status 400. An empty POST body SHALL be read as an empty object. A rejected request SHALL change no Recording_State.
3. WHEN a valid `POST /api/record/start` arrives and the Recording_State is `idle`, `done` or `error`, THE Recording_Manager SHALL set the Recording_State to `recording`, SHALL answer status 202, and SHALL open a visible (not headless) browser on the given web address with the recording panel.
4. WHILE the Recording_State is `recording`, `saving` or `compiling`, THE Recording_Manager SHALL answer every `POST /api/record/start` with status 409 and SHALL leave the active Recording_Session unchanged.
5. FOR ALL sets of N ≥ 2 concurrent `POST /api/record/start` requests that are valid and arrive while the Recording_State is `idle`, `done` or `error`, THE Recording_Manager SHALL answer exactly one with status 202, SHALL answer the other N−1 with status 409, and SHALL open exactly one browser.
6. WHEN a valid `POST /api/record/stop` arrives while the Recording_State is `recording`, THE Recording_Manager SHALL abort the `RecordOptions.signal` of the session, which calls `LiveRecorder.requestEnd('signal')`, SHALL set the Recording_State to `saving` before it answers, and SHALL answer status 202.
7. WHEN the user activates "Finish and save" in the recording panel while the Recording_State is `recording`, THE Recording_Manager SHALL end the session through `LiveRecorder.requestEnd('panel')`, which takes the same completion path (`completeRecording`) as Criterion 6, and SHALL set the Recording_State to `saving`.
8. IF a valid `POST /api/record/stop` arrives while the Recording_State is `idle`, `saving`, `compiling`, `done` or `error`, THEN THE Recording_Manager SHALL answer status 409 and SHALL change no state.
9. THE Recording_Manager SHALL change the Recording_State only through these transitions: `idle`, `done` or `error` to `recording` on a start accepted under Criterion 3; `recording` to `saving` when the session end is requested (Criterion 6 or 7) or when the user closes the browser; `saving` to `compiling` when `completeRecording` has saved the workflow; `compiling` to `done` when `compile()` succeeds; and `recording`, `saving` or `compiling` to `error` when the browser cannot be opened, `completeRecording` fails or `compile()` fails.
10. WHEN `GET /api/record/status` arrives, THE Studio_API SHALL answer status 200 with the Recording_State, the step count (0 while the state is `idle`), the labels of the last 3 recorded steps (or all of them when fewer than 3 exist), and, only while the state is `error`, an error message and the recovery file location when one was written.
11. THE Studio_API SHALL answer `GET /api/record/status` with step labels only, SHALL NOT include any value the user typed into a field, and SHALL pass the answer through the Redactor.
12. IF the recording fails, THEN THE Recording_Manager SHALL set the Recording_State to `error`, SHALL keep the browser closed and any already saved workflow unchanged, and SHALL report a plain-language message that contains no secret value.
13. IF the user closes the browser or the page crashes while at least one step was recorded, THEN THE Recording_Manager SHALL keep the recovery file that `completeRecording` writes, SHALL set the Recording_State to `error`, and SHALL report the recovery file location in the status. IF the user closes the browser before any step was recorded, THEN THE Recording_Manager SHALL set the Recording_State to `error`, report that nothing was recorded, and write no file.
14. WHEN a Recording_Session reaches `done` or `error`, THE Recording_Manager SHALL accept a new `POST /api/record/start`, and the status SHALL keep reporting the final state, step count and labels until that start is accepted.
15. WHEN the Studio closes while the Recording_State is `recording`, `saving` or `compiling`, THE Recording_Manager SHALL end the session through the `RecordOptions.signal` path and close its browser within 10 seconds.
16. IF the request body of `POST /api/record/start` contains a field other than the action name, the web address and the reuse choice, or an invalid action name or web address (Requirement 3, Criteria 7 and 8), THEN THE Studio_API SHALL answer status 400 with a plain-language message, SHALL NOT open a browser, and SHALL leave the Recording_State unchanged.
17. WHILE the Recording_State is `recording`, `saving` or `compiling`, THE Studio_UI SHALL poll `GET /api/record/status` at an interval of at most 2000 ms and SHALL show the Recording_State, the step count and the last 3 step labels on a status screen. WHEN the state becomes `done` or `error`, THE Studio_UI SHALL show the final state and stop polling.
18. IF `GET /api/record/status` fails or answers with a status other than 200 while the Studio_UI is polling, THEN THE Studio_UI SHALL keep the last known values, show a plain-language "connection lost" message, and retry at the same interval.

### Requirement 5: Browser fallback

**User Story:** As a user without Playwright's Chromium, I want recording to use a browser already on my computer, so that I do not have to install anything extra.

#### Acceptance Criteria

1. WHERE the `DAEMONIZE_CHROMIUM_PATH` environment variable is set to a non-empty value, THE Browser_Launcher SHALL launch the browser at that path with no `channel` option, and SHALL make exactly one launch attempt.
2. IF the launch at the `DAEMONIZE_CHROMIUM_PATH` path fails for any reason, including a missing file, THEN THE Browser_Launcher SHALL NOT try bundled Chromium, `chrome` or `msedge`, and SHALL fail with a plain-language message that names `DAEMONIZE_CHROMIUM_PATH`, the configured path, and the underlying reason.
3. WHEN `DAEMONIZE_CHROMIUM_PATH` is unset or an empty string, THE Browser_Launcher SHALL try the browsers in this order and no other: (1) Playwright's bundled Chromium, launched with neither `executablePath` nor `channel`; (2) Google Chrome, launched with channel `chrome`; (3) Microsoft Edge, launched with channel `msedge`. THE Browser_Launcher SHALL stop at the first browser that launches and SHALL make at most 3 launch attempts.
4. IF a launch attempt in Criterion 3 fails because the browser executable is not installed, THEN THE Browser_Launcher SHALL make the next attempt in the order of Criterion 3. A launch failure counts as "not installed" only when the Playwright launch error message states that the executable does not exist, or that the `chrome` or `msedge` distribution is not found. Any other launch failure is handled by Criterion 5.
5. IF a launch attempt in Criterion 3 fails for any reason other than "not installed" as defined in Criterion 4 (for example permission denied, a browser process that exits at startup, no display available, or the 30-second Playwright launch timeout), THEN THE Browser_Launcher SHALL make no further attempt and SHALL fail with a plain-language message that names the browser that failed and the underlying reason.
6. IF all 3 attempts in Criterion 3 fail because the browser is not installed, THEN THE Browser_Launcher SHALL fail with a plain-language message that names Google Chrome and Microsoft Edge as browsers the user can install and names `DAEMONIZE_CHROMIUM_PATH` as the manual option.
7. THE Browser_Launcher SHALL accept the `headless` option and apply it to every attempt. WHEN a browser is launched, THE Browser_Launcher SHALL report which of bundled Chromium, `chrome`, `msedge` or the `DAEMONIZE_CHROMIUM_PATH` path was used. This report SHALL NOT appear in the Studio_API responses.
8. THE `record` command of the Daemonize_CLI SHALL launch its browser through the Browser_Launcher, with the order and behaviour of Criteria 1 to 7 and with `headless` defaulting to false. IF the Browser_Launcher fails, THEN THE `record` command SHALL write the failure message to standard error, exit with a non-zero code, create no Workflow_File content and create no recovery file.
9. IF the Browser_Launcher fails during a Studio-started Recording_Session, THEN THE Recording_Manager SHALL set the Recording_State to `error` and report the failure message of the Browser_Launcher in `GET /api/record/status`, with no secret value and no file written.
10. THE replay browser launch of `PlaywrightDriver` in `src/sandbox/playwright-driver.ts` SHALL keep its current behaviour: a single headless launch of bundled Chromium, or of the `DAEMONIZE_CHROMIUM_PATH` path when it is non-empty, with no fallback to `chrome` or `msedge`.

### Requirement 6: Optional persistent session per application

**User Story:** As a user whose application needs a login and a 2FA code, I want to sign in once and reuse that session, so that I do not repeat the login on every recording.

#### Acceptance Criteria

1. THE Session_Store SHALL keep at most one saved storage state per Application_Key, in the App_Data_Dir, in a file whose name is derived from a hash of the Application_Key and ends with `.storage-state.json`, so that equal Application_Keys map to the same file and different Application_Keys map to different files.
2. THE Studio SHALL resolve the App_Data_Dir so that it is not equal to and not inside any of the following: the current working directory, any directory at or above the current working directory that contains a `.git` folder, and the Output_Dir.
3. IF the resolved App_Data_Dir is equal to or inside a location excluded by Criterion 2, THEN THE Studio SHALL create no file in it, SHALL neither read nor save any session, SHALL show a plain-language error in the Studio_UI, and SHALL let the Recording_Session proceed without a stored session.
4. WHERE the user selected "Reuse my signed-in session", WHEN a Recording_Session starts and the Session_Store holds a readable saved storage state for the Application_Key, THE Recording_Manager SHALL start the browser with that storage state.
5. WHERE the user selected "Reuse my signed-in session", WHEN a Recording_Session starts and the Session_Store holds no usable saved storage state for the Application_Key (none exists, or Criterion 14 applies), THE Recording_Manager SHALL start the browser without a storage state.
6. WHERE the user selected "Reuse my signed-in session", WHEN a Recording_Session ends with the state `done`, THE Recording_Manager SHALL save the browser storage state of that session in the Session_Store for its Application_Key, replacing any earlier one. WHEN a Recording_Session ends with the state `error`, THE Recording_Manager SHALL leave the saved storage state of that Application_Key unchanged.
7. THE Studio_API SHALL expose, for each application that has an Action in the Workflow_File, only the Application_Key and a boolean "saved session available", with no cookie, token, header or storage-state content, and no file name or path of the Session_Store.
8. WHEN a valid `POST /api/sessions/forget` arrives with an Application_Key, THE Studio SHALL delete the saved storage state file of that Application_Key if it exists and SHALL answer with "saved session available" equal to false, also when no file existed.
9. THE Studio_Guard SHALL apply to `POST /api/sessions/forget` exactly as it applies to the playground POST routes, and a request that fails any Studio_Guard check SHALL delete no file.
10. THE Session_Store SHALL write only inside the App_Data_Dir, which Criterion 2 keeps outside every directory the Secret_Scan reads. The Secret_Scan reads only the files that git lists as tracked or as untracked and not ignored, so it SHALL NOT be changed to read the App_Data_Dir.
11. THE Studio SHALL NOT write a storage state file, or the path of a Session_Store file, into the repository, the Output_Dir, the Workflow_File or any `.assets` folder.
12. THE Redactor SHALL replace every cookie value and local-storage value of a saved storage state, when it has three or more characters, with `***` in every Studio response, and SHALL drop the `cookies`, `origins`, `localStorage` and `sessionStorage` members.
13. THE Studio_UI SHALL show, for the application of an Action, the text "Saved session available: yes" or "Saved session available: no" and a "Forget session" button that is enabled only when the answer is yes.
14. IF a saved storage state file is unreadable, is not valid JSON, or has no `cookies` array and no `origins` array, THEN THE Studio SHALL treat the session as not available, SHALL report "no" without exposing the file content, and SHALL let the Recording_Session proceed without a storage state.
15. IF the Recording_Manager cannot save the storage state under Criterion 6, THEN THE Recording_Manager SHALL keep the Recording_State `done`, SHALL show a plain-language error that says the session was not saved, and SHALL keep the earlier saved storage state of that Application_Key unchanged.
16. IF the user did not select "Reuse my signed-in session", THEN THE Recording_Manager SHALL neither read nor write the Session_Store for that Recording_Session.

### Requirement 7: Automatic compilation

**User Story:** As a user, I want my recording to become a usable tool without a second step, so that I can test it right away.

#### Acceptance Criteria

1. WHEN a Studio-started Recording_Session ends with success, THE Compile_Runner SHALL start `compile()` on the Workflow_File into the Output_Dir within 1 second, and THE Recording_State SHALL become `compiling` before `compile()` starts.
2. WHEN a valid `POST /api/compile` arrives while the Compile_State is not `running`, THE Compile_Runner SHALL start `compile()` on the Workflow_File into the Output_Dir and THE Studio_API SHALL answer status 202.
3. WHEN the user activates the "Recompile" button, THE Studio_UI SHALL send `POST /api/compile`.
4. IF the directory `<Output_Dir>/node_modules` does not exist when the Compile_Runner starts, THEN THE Compile_Runner SHALL call `compile()` with `install: true`.
5. IF the directory `<Output_Dir>/node_modules` exists when the Compile_Runner starts, THEN THE Compile_Runner SHALL call `compile()` with `install` unset.
6. THE Compile_Runner SHALL pass to `compile()` the options that `daemonize compile` uses when no flag is given, which are `http` off, no `healSupport`, no `suggest` and no `sandbox`.
7. THE Studio_API SHALL answer `GET /api/compile/status` with the Compile_State, the current phase, and an error message when the Compile_State is `error`. The phase SHALL be `generating` while `compile()` writes the Output_Dir and its property tests, `installing` while the dependencies are installed, and null when the Compile_State is not `running`.
8. WHEN the Compile_Runner finishes with success, THE Compile_State SHALL become `done`, THE Recording_State SHALL become `done` if it was `compiling`, and THE Studio SHALL call `PlaygroundSession.stop()` so that the next playground call starts the Child_Server from the new output.
9. IF the phase `installing` lasts longer than 600 seconds, THEN THE Compile_Runner SHALL end the installation and treat it as a `compile()` failure.
10. IF `compile()` fails before it writes the first file of the Output_Dir, THEN THE Compile_Runner SHALL leave every file of the Output_Dir unchanged, set the Compile_State to `error`, and report a plain-language message without any secret value.
11. IF `compile()` fails after it wrote the first file of the Output_Dir, which includes a failure of property-test generation or of the installation, THEN THE Compile_Runner SHALL set the Compile_State to `error`, call `PlaygroundSession.stop()`, and report a plain-language message without any secret value that says the Output_Dir may be incomplete and that "Recompile" can be repeated.
12. IF `compile()` fails and the Recording_State is `compiling`, THEN THE Recording_State SHALL become `error`, and THE Studio SHALL keep the Workflow_File with the recorded Action unchanged.
13. WHILE the Compile_State is `running`, THE Studio_API SHALL answer every further `POST /api/compile` with status 409 and leave the running compilation unchanged.
14. THE Studio_Guard SHALL apply to `POST /api/compile` and to `GET /api/compile/status` exactly as it applies to the existing playground routes.
15. WHEN the Compile_State becomes `done`, THE Studio_UI SHALL show a "Test it" button that opens the playground with the new Action selected.

### Requirement 8: Guided secrets vault

**User Story:** As a user, I want to type my password and 2FA key once in a clear panel, so that I never touch environment variables.

#### Acceptance Criteria

1. THE Secret_Vault SHALL keep every secret value in the App_Data_Dir only in a form that is encrypted or protected by the operating system.
2. THE Secret_Vault SHALL NOT write any secret value in plain text to disk, to the repository, to `daemonize.workflows.json`, to the Output_Dir, to the system temporary folder or to a Studio log line.
3. THE Secret_Vault SHALL be write-only through the Studio_API: no route SHALL return a stored secret value, in whole or in part, or its length.
4. WHEN `GET /api/secrets` arrives, THE Studio_API SHALL answer status 200 with one entry for each distinct Secret_Name required by any Action of the Workflow_File, sorted by name. The required names SHALL be those of the compiled mode without `--http`: the declared secrets and the `secretRef` of the steps. Each entry SHALL contain exactly three fields: `name`, `kind` (`password`, `totp` or `token`) and a boolean `configured`. Kind SHALL be determined in this order: the declared kind, with the declared kind `header` reported as `token`; `totp`, when a step that references the name has `totp` set to true; `password`, in every other case. When the Workflow_File does not exist, the list SHALL be empty.
5. WHERE a required secret is held in the Secret_Vault, or is provided as a non-empty `DAEMONIZE_SECRET_<NAME>` variable by the Studio environment or by a literal entry of the `env` of `mcp.json`, THE Studio_API SHALL report it as `configured: true` in `GET /api/secrets`. The variable name SHALL be matched without regard to case against the upper-cased Secret_Name. A secret that is in neither place SHALL be reported as `configured: false`.
6. WHEN a valid `POST /api/secrets` arrives with a Secret_Name that an Action requires and a value that satisfies Criterion 9, THE Secret_Vault SHALL store the value, or replace the existing one, and THE Studio_API SHALL answer status 200 with a body that contains only `name` and `configured: true`. For a `password` or `token` secret the value SHALL be stored byte for byte, without trimming.
7. THE Studio_Guard SHALL apply to `POST /api/secrets` exactly as it applies to the playground POST routes. A request without the token, with a foreign Origin, with a foreign Host, or without the `x-studio-request` header SHALL be answered with status 401 or 403 and SHALL change nothing in the Secret_Vault.
8. IF `POST /api/secrets` names a Secret_Name that is not required by any Action of the Workflow_File, THEN THE Studio_API SHALL answer status 400 and store nothing. The name SHALL be compared exactly, with case.
9. IF the value of `POST /api/secrets` is missing, is not a string, is shorter than 3 characters, is longer than 4096 bytes in UTF-8, or contains a NUL character, THEN THE Studio_API SHALL answer status 400 with a plain-language message that does not repeat the value, and SHALL store nothing. The minimum of 3 characters is the length below which the Redactor does not scrub a value (`MIN_SECRET_LENGTH`).
10. WHEN a valid `POST /api/secrets` arrives for a secret of Secret_Kind `totp` with a Base32_Secret, THE Secret_Vault SHALL store the normalized form of that Base32_Secret. Normalization SHALL (1) remove every whitespace character and every `-`; (2) remove trailing `=` characters; (3) convert to upper case. The normalized form SHALL consist only of the characters `A-Z` and `2-7` and be at least 3 characters long. It SHALL decode (`decodeBase32` of `src/replay/runtime/totp.ts`) to the same bytes as the submitted value. A `=` anywhere other than at the end SHALL make the value invalid.
11. WHEN a valid `POST /api/secrets` arrives for a secret of Secret_Kind `totp` with an Otpauth_URI of type `totp`, THE Studio SHALL read the single `secret` query parameter after percent-decoding and normalize it as in Criterion 10. It SHALL store only that Base32_Secret, and SHALL NOT store or retain any other part of the URI (label, `issuer`, `digits`, `period`, `algorithm`). An Otpauth_URI with no `secret` parameter, with more than one `secret` parameter, or of a type other than `totp` SHALL be handled as in Criterion 13.
12. FOR ALL valid Base32_Secrets S, with any mix of upper and lower case, any padding and any grouping separators, and for any Otpauth_URI label and extra parameters, THE extraction SHALL satisfy `extract(build(S)) = normalize(S)` and `normalize(normalize(S)) = normalize(S)` (round-trip and idempotence property). `build(S)` is an Otpauth_URI whose `secret` parameter is S, percent-encoded as needed.
13. IF a value for a `totp` secret is neither a valid Base32_Secret nor an Otpauth_URI with a valid Base32 `secret` parameter, THEN THE Studio_API SHALL answer status 400 with a plain-language message that contains no part of the submitted value, and SHALL store nothing. A value already stored under that name SHALL remain unchanged and the Child_Server SHALL NOT be stopped.
14. THE Redactor SHALL treat every value in the Secret_Vault, and for a `totp` secret its normalized Base32_Secret, as a known secret value on every Studio_API route. No response body, no key or value of a response, no call history entry, no playground answer, no failure text or screenshot caption, and no error message SHALL contain such a value.
15. FOR ALL secret values set through `POST /api/secrets` (3 to 4096 bytes, and for `totp` also the submitted forms of Criteria 10 and 11), THE Studio SHALL ensure that no Studio_API response body or header on any route, no log line written by the Studio, and no file under the repository, the Output_Dir, the system temporary folder or the App_Data_Dir contains the value in plain text (property). The only exception is a value made only of `*` characters, which equals the redaction mark.
16. WHEN a Secret_Vault value is set, replaced or removed and the Child_Server is running, THE Studio SHALL stop the Child_Server before it sends the response to that request, so that the next start receives the new values. A request that is rejected SHALL NOT stop the Child_Server.
17. WHEN a valid `POST /api/secrets/forget` arrives with a Secret_Name that an Action requires or that is held in the Secret_Vault, THE Secret_Vault SHALL delete that secret, and THE Studio_API SHALL answer status 200 with only `name` and `configured` as defined in Criterion 5. A Secret_Name that is neither required nor stored SHALL be answered with status 400. THE Studio_Guard SHALL apply to this route as stated in Criterion 7.
18. IF the operating system protection of the Secret_Vault is unavailable when `POST /api/secrets` arrives, THEN THE Studio_API SHALL answer status 503 with a plain-language message, SHALL store nothing, SHALL leave the values already stored unchanged, and SHALL NOT fall back to plain text storage.
19. WHEN a secret value is set or replaced, THE Studio SHALL add that value to the Redactor's known secret values before it sends the response to that request.
20. IF the content of the Secret_Vault cannot be read or decrypted, THEN THE Studio_API SHALL report the affected secrets as `configured: false` (unless Criterion 5 reports them as configured through the environment), SHALL NOT return any of that content, and SHALL accept a later valid `POST /api/secrets` that replaces the secret.

### Requirement 9: Secrets reach only the child server

**User Story:** As a user, I want my stored credentials to be used when I test a tool, and nowhere else, so that they stay private.

#### Acceptance Criteria

1. WHEN the Playground_Session starts the Child_Server, THE Playground_Session SHALL set in the Child_Server environment one variable `DAEMONIZE_SECRET_<NAME>`, with the Secret_Vault value as its value, for each Secret_Name that the workflows in the Output_Dir require and for which the Secret_Vault holds a non-empty value.
2. THE Playground_Session SHALL pass Secret_Vault values only to the Child_Server, and SHALL NOT set them in the environment of any other process, in the environment of the Studio process (`process.env`), or in any command-line argument of any process.
3. WHEN the Playground_Session builds the Child_Server environment, IF a variable `DAEMONIZE_SECRET_<NAME>` is set in the Studio environment or in the literal `env` entries of the `mcp.json` and the Secret_Vault also holds a non-empty value for `<NAME>`, THEN THE Playground_Session SHALL give the Child_Server the Secret_Vault value and SHALL NOT give it the other value.
4. IF the Secret_Vault holds no non-empty value for a required Secret_Name and a non-empty `DAEMONIZE_SECRET_<NAME>` is set in the Studio environment or in the literal `env` entries of the `mcp.json`, THEN THE Playground_Session SHALL pass that value to the Child_Server unchanged.
5. WHEN `configuredSecretVariables()` is called, THE Playground_Session SHALL return the set of upper-case names `DAEMONIZE_SECRET_<NAME>` whose value in the Child_Server environment (Secret_Vault, Studio environment or `mcp.json`) is non-empty, and SHALL return no value.
6. WHEN the Studio_UI shows a tool in the playground, THE Studio_UI SHALL show for each secret that the tool requires either "configured" or "missing", using the same `configured` flag as `GET /api/secrets`.
7. WHILE at least one required secret of the selected tool is missing, THE Studio_UI SHALL show a notice with a link to the credentials panel next to the "Test" button.
8. THE Studio SHALL NOT write a Secret_Vault value to the `mcp.json`, to the generated `mcp-server.js`, to the Kiro_Power, to the call history, or to any file in the Output_Dir.
9. THE Playground_Session SHALL include in the Child_Server environment a Secret_Vault value only under a name of the form `DAEMONIZE_SECRET_<NAME>`, for all values stored in the Secret_Vault.
10. WHEN the Studio sends any response of the Studio_API or records an entry in the call history, THE Studio SHALL replace each Secret_Vault value that the response or entry contains with a redaction marker.
11. IF the Secret_Vault cannot be read when the Playground_Session starts the Child_Server, THEN THE Playground_Session SHALL NOT start the Child_Server, SHALL return an error that names the failure and contains no secret value, and SHALL leave the Secret_Vault unchanged.

### Requirement 10: Credentials panel in the Studio

**User Story:** As a user, I want one screen that lists the credentials my action needs and lets me fill them in, so that I know what is missing before I test.

#### Acceptance Criteria

1. WHEN the user activates the "Credentials" link, which the Overview, the workflow view and the playground each contain, THE Studio_UI SHALL display the credentials panel within 1 second, with no full page reload.
2. THE credentials panel SHALL list every secret that any Action requires, using the secrets returned by `GET /api/secrets`. Each entry SHALL show a plain-language name (the Secret_Name in sentence case, with underscores replaced by spaces, and never the text `DAEMONIZE_SECRET_<NAME>`) and its Secret_Kind. The Secret_Kind SHALL read "Password" for `password`, "Authenticator key" for `totp` and "Access code" for `token`. Each entry SHALL also show the status "Configured" when `configured` is `true`, otherwise "Missing". The status SHALL be conveyed by its text and not by color alone.
3. THE credentials panel SHALL provide for each secret one masked input (type `password`) that accepts 3 to 4096 bytes, and a "Save" button. The "Save" button SHALL be disabled while the input has fewer than 3 characters and while a save request for that secret is pending. THE credentials panel SHALL show a "Remove" button for a secret only while its status is "Configured".
4. THE credentials panel SHALL provide for each "Authenticator key" input the ability to accept either the Base32_Secret or the full text of the Otpauth_URI. It SHALL also provide non-empty help text, linked to the input with `aria-describedby`, that says the key appears next to the QR code when the user turns on two-step verification in the application.
5. WHEN a save request returns success, THE credentials panel SHALL, within 1 second, clear the input, set the status of that secret to "Configured", show its "Remove" button, and write a message naming the secret (not its value) to the polite live region `#live`.
6. IF a save request returns an error status, returns no response within 10 seconds, or fails at the network level, THEN THE credentials panel SHALL clear the input and keep the previous status. It SHALL show next to that secret a plain-language error with `role="alert"` that states the reason (invalid value, not allowed, store unavailable or no answer) and does not repeat the submitted value. It SHALL also re-enable the "Save" button once the input has at least 3 characters.
7. THE Studio_UI SHALL NOT place a secret value in the URL, in the hash route, in `localStorage`, in `sessionStorage`, in a cookie, in an element attribute, or in a text node. The only exception is the `value` property of the masked input while the user types or while a save request is pending, and the Studio_UI SHALL clear it when that request completes, whether it succeeds or fails.
8. THE credentials panel SHALL give each input `autocomplete="off"` and a visible text label, associated with the input through `for` and `id`. A placeholder SHALL NOT replace that label.
9. WHEN the user activates "Remove" for a configured secret and `POST /api/secrets/forget` returns success, THE credentials panel SHALL, within 1 second, set the status of that secret to "Missing", hide its "Remove" button, and write a message naming the secret to the polite live region `#live`.
10. IF the request from "Remove" returns an error status, returns no response within 10 seconds, or fails at the network level, THEN THE credentials panel SHALL keep the status "Configured" and show next to that secret a plain-language error with `role="alert"`.
11. IF `GET /api/secrets` lists no required secret, THEN THE credentials panel SHALL show the text "No credentials needed" and no input. IF the request itself fails, THEN THE credentials panel SHALL show a plain-language error with `role="alert"` and a "Retry" button, and no input.

### Requirement 11: One-click connection to Kiro and MCP clients

**User Story:** As a user, I want a button that connects my tool to Kiro, and another that copies the configuration for other clients, so that I do not edit JSON.

#### Acceptance Criteria

1. WHILE the Compile_State is `done` and `mcp-server.js` exists in the Output_Dir, THE Studio_UI SHALL show a "Connect to Kiro" action and a "Copy MCP configuration" button.

The screen SHALL display the exact absolute path of the target `.kiro/` folder. For each file that will be written, it SHALL display the path relative to `.kiro/` and one of three outcomes: "create", "merge" (an existing `settings/mcp.json` that gets one entry added or replaced), or "replace" (an existing file that gets overwritten).

WHEN a confirmed `POST /api/power/install` arrives, THE Power_Installer SHALL write exactly two things into the `.kiro/` folder of the Target_Workspace, creating missing folders: the MCP server entry (one entry under `mcpServers` in `settings/mcp.json`, keyed by the Kiro_Power name, with the `command`, `args` and `env` values that the Kiro_Power's `mcp.json` holds) and the skill file (the Kiro_Power's `SKILL.md` at `skills/<Kiro_Power name>/SKILL.md`).

IF a file that the Power_Installer would write already exists in the target `.kiro/` folder, THEN THE Power_Installer SHALL list it on the confirmation screen and SHALL overwrite or merge it only after the confirmation. IF `settings/mcp.json` already holds an entry under the same key, THEN THE confirmation screen SHALL state that this entry will be replaced.

IF the existing `settings/mcp.json` in the target `.kiro/` folder is not valid JSON, or its `mcpServers` member is present and is not an object, THEN THE Power_Installer SHALL refuse with status 409, leave that file byte-identical, write no other file, and THE Studio_UI SHALL show an error naming the file.
18. WHEN the install succeeds, THE Studio_UI SHALL list the names of the Secret_Placeholders written (for example `DAEMONIZE_SECRET_TOTP`) and SHALL state that each must be set in the environment Kiro runs in. WHEN the install merges into an existing `settings/mcp.json`, every other `mcpServers` entry SHALL remain equal to its previous value.
19. WHERE the user selects "Add as a Kiro Power instead", THE Studio_UI SHALL show the absolute path of the Output_Dir, which holds `POWER.md` and `mcp.json`, and SHALL show the steps to import it in Kiro through the Powers panel from a local folder. THE Studio SHALL write no file for this option.

### Requirement 13: Security and non-regression

**User Story:** As a user and as an owner of the repository, I want every new capability to keep the Studio's existing guarantees, so that adding convenience does not add exposure.

#### Acceptance Criteria

1. WHEN the Studio starts without a `--host` value, THE Studio SHALL listen only on 127.0.0.1, and every new route (`/api/record/*`, `/api/secrets*`, `/api/sessions/forget`, `/api/compile*`, `/api/power/*`) SHALL be served by that same listener through the Studio_Guard. This includes the status codes already defined in Requirements 4.2, 6.9, 7.14, 8.7 and 11.13: 414 for a URL longer than 2048 characters, 403 for a Host or Origin that is not the Studio's own, and 401 for a missing or invalid token. It also includes 401 for a cookie-authenticated POST that lacks the `x-studio-request` header or an allowed Origin.
2. IF the Studio listens on an address that is not loopback because `--allow-remote` was given, THEN THE Studio SHALL answer every request to `/api/record/*`, `/api/secrets*`, `/api/sessions/forget`, `POST /api/compile` and `/api/power/*` with status 403 and a plain-language message. These routes SHALL change no state and start no process.
3. THE Studio SHALL read at most 64 KiB of request body on every new POST route and answer a larger body, whether declared by `Content-Length` or counted while reading, with status 413 and a closed connection.
4. IF a new POST route receives a non-empty body whose `Content-Type` is not `application/json`, THEN THE Studio SHALL answer status 415 and change no state.
5. IF a new route receives a method other than the one it defines (`GET` or `HEAD` for status routes, `POST` for action routes), THEN THE Studio SHALL answer status 405 with an `Allow` header that lists the defined methods.
6. THE Studio SHALL send every JSON answer of the new routes through the Redactor.
7. THE Studio SHALL send the same response headers on the new routes as on the existing routes, including `Content-Security-Policy` with `default-src 'self'`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: no-store`. It SHALL send no `Access-Control-*` header.
8. THE Studio SHALL NOT write a secret value to standard output, standard error, a log file, a stack trace shown to the user, a recovery file, a thumbnail, an `.assets` file or a generated file of the Output_Dir. The properties in Requirements 8.15 and 11.6 cover the responses and files they name.
9. IF a field of a request to a new route that expects a plain name contains a `..` segment, an absolute path, or a NUL character, THEN THE Studio SHALL answer status 400 and read, write or delete no file. Requirement 11 Criterion 9 defines the Target_Workspace path, which is not a plain name.
10. WHEN the Studio starts, THE Studio SHALL start no Recording_Session, no compile and no install. THE Studio SHALL start one only after a request that passed the Studio_Guard.
11. THE existing automated tests of the Studio server, playground, redaction, recording panel and compiler SHALL pass; an existing test may change only where this spec changes the behaviour it asserts, and each such change SHALL be listed in the tasks. The CLI non-regression is stated in Requirement 1 Criterion 6.
12. THE `.gitignore` of the repository SHALL ignore every file name that the Studio or the Browser_Launcher uses as a fallback location for a saved storage state. `git check-ignore` SHALL report each of those names as ignored.

### Requirement 14: Tests

**User Story:** As a maintainer, I want automated tests for each new behaviour, so that later changes cannot break the security guarantees unnoticed.

#### Acceptance Criteria

1. THE test suite SHALL place every test in one of three folders: `tests/unit` (fast, no external service), `tests/property` (fast-check properties), or `tests/integration` (real browser, pseudo-terminal, MCP server or container). THE test suite SHALL name each file `*.test.ts`, so that the `fast` project of `vitest.config.ts` (unit and property) and the `integration` project (maximum 2 workers) each pick it up.
2. WHEN a maintainer runs `npm test`, THE test suite SHALL run the `fast` project and then the `integration` project through `vitest run`, and the command SHALL exit with code 0 only if every test of both projects passes. `npm run test:unit`, `npm run test:property` and `npm run test:integration` SHALL each run only their folder.

4. THE test suite SHALL contain integration tests of `/api/record/start`, `/api/record/status` and `/api/record/stop` that use a real visible browser. One test SHALL end the session with `POST /api/record/stop` and one SHALL end it with "Finish and save" in the recording panel. Each test SHALL prove: start answers 202; a second start answers 409 and leaves the session unchanged; `GET /api/record/status` returns the state, the step count and at most 3 step labels; no value typed into a field appears in the status; and a stop outside the `recording` state answers 409 and changes no state (Requirement 4, Criteria 3 to 10).

THE test suite SHALL contain tests of `POST /api/secrets` and `GET /api/secrets` that prove: no response returns a stored value; the response to a save contains only the Secret_Name and `configured: true`; a Base32_Secret is stored upper-cased without spaces; an Otpauth_URI is reduced to its `secret` parameter; an invalid `totp` value, an empty value, a value over 4096 bytes and an unrequired Secret_Name each answer 400 and store nothing; and a request without the token, with a foreign Origin, with a foreign Host, or without the `x-studio-request` header answers 401 or 403 and leaves the Secret_Vault unchanged (Requirement 8, Criteria 3 to 13).
7. THE test suite SHALL contain a property test that, for every generated Base32_Secret of 16 to 64 characters, builds an Otpauth_URI, extracts the `secret` parameter, and checks that the result equals the normalized original, with at least 100 generated cases (Requirement 8, Criterion 12).
8.
